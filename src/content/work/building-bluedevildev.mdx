## How a form becomes a lead

Nothing in the browser talks to the CRM. Each form posts to a server route that runs the same steps in the same order, so a new form gets the same protection as the old ones.

<Exhibit caption="lead intake">

```text
form submit
  ─► validate on the server     reject bad input
  ─► spam and abuse checks      drop bots quietly
  ─► find or create contact     no duplicate people
  ─► create lead                with follow-up tasks
  ─► confirmation email         to the sender
```

</Exhibit>

Site content follows the same rule as code. It is written into a versioned seed script and loaded from there, so a copy change is reviewed and tested before it reaches the site, and nothing lives only in an admin panel.

## Releases I can undo

A change moves from a feature branch to staging to production, and each step deploys automatically. Five checks run in parallel before anything merges: policy and formatting, the application tests, a security scan, CMS integration tests against a real database, and a full build with end-to-end, accessibility and performance tests. Every image a server runs is pinned to an exact version, and a release only counts once a public smoke test passes. A rollback will not start a CMS version older than its database, because that is the one rollback that destroys data.

## Recovery, measured

Backups leave the server every day, and a scheduled workflow fails loudly if one is missing. Once a quarter, a drill restores the latest backup into an isolated environment and checks the content against what the site should hold. The targets are written down and approved: lose at most 24 hours of data, and be back within 4 hours. The first drill restored the database and CMS in 57 seconds, from a backup under 20 minutes old.
